# Monorepo Structure

AverisOS uses a **monorepo** structure with domain-bounded contexts that can be extracted to separate services in Phase 3+.

## Why Monorepo?

- **MVP speed**: Develop domains together during validation phase
- **Shared code**: Common patterns, error types, repositories
- **Cross-domain changes**: Single PR for changes affecting multiple domains
- **Future extraction**: Clear domain boundaries make extraction straightforward

See [ADR-003: Monorepo for Domains](../decisions/adr-003-monorepo.mdx) for full rationale.

## Key Directories Explained

### `/domains/shared`

**Purpose**: Shared code used across all domains.

**Contains**:
- `EventDispatcher` for cross-domain communication
- Base repository class
- Common error types
- Shared utilities

Result/error handling itself is `dry-monads` (see [ADR-002](../decisions/adr-002-result-monad.mdx)) — a gem dependency, not domain-specific code, so it isn't part of `shared`.

**Who uses it**: Every domain imports from `shared`.

**Example**:
```ruby
# In any domain
include Dry::Monads[:result]

result = Success(artifact)
return result.bind { |a| next_operation(a) }
```

---

### `/domains/[domain_name]/domain`

**Purpose**: Business logic for a specific domain.

**Contains**:
- Service entry point (`[domain]_service.rb`)
- Operations (Request/Verify/Validate/Command)
- Domain events
- Domain-specific exceptions

**Pattern**:
```
domains/traceability/domain/
├── traceability_service.rb     # Entry point
├── create_artifact/            # Operation
│   ├── request.rb
│   ├── request_factory.rb
│   ├── verify.rb
│   ├── validate.rb
│   └── command.rb
├── link_artifacts/             # Operation
│   ├── request.rb
│   ├── request_factory.rb
│   ├── verify.rb
│   ├── validate.rb
│   └── command.rb
└── events/                      # Domain events
    ├── artifact_created.rb
    └── artifacts_linked.rb
```

A `Command` that subclasses `AverisOS::BaseCommand` (`app/lib/averis_os/base_command.rb`
— a gem-adjacent app-level base class, not `domains/shared`, since it isn't
domain-specific) gets its `Verify -> Validate -> perform` wiring for free; the
service just calls `Command.new.call(request)`. See
[Patterns & Examples](./patterns.mdx#pattern-1-operation-with-simple-validation)
for the full example (currently adopted by `authentication`).

---

### `/app/controllers`

**Purpose**: HTTP routing and serialization only.

**Contains**:
- Rails controllers grouped by API version
- Serializers for domain models
- No business logic

**Pattern**:
```ruby
module Api
  module V1
    class ArtifactsController < ApplicationController
      def create
        service = AverisOS::Container['domains.traceability']
        result = service.create_artifact(create_params)

        if result.success?
          render json: ArtifactSerializer.new(result.value!), status: 201
        else
          render json: { error: result.failure }, status: 422
        end
      end
    end
  end
end
```

---

### `/app/structs`

**Purpose**: Typed shapes for data crossing a domain boundary — a `Command`'s
success value, or any other POJO/POCO-style payload handed from domain
operations out to controllers (or between domains). Not business logic, so
it doesn't belong in `domains/*/domain`; it's the app-level equivalent of
`domains/shared/lib` for the outward-facing side of the dependency flow.

**Contains**:
- `Dry::Struct` value objects returned by domain `Command`s, with attributes
  typed via `dry-types` (`Types = Dry.Types()`, defined once in
  `app/structs/types.rb`) rather than left as untyped `Struct.new` fields

**Rule**: struct attributes are plain data (ids as `Types::Strict::String` —
primary keys are UUIDs, see `db/schema.rb` — plus strings/times/etc.), never
`Types.Instance(SomeActiveRecordModel)`. A `Command` holds the AR object only
long enough to pull the fields it needs; the AR instance itself never crosses
back out to a controller. If a controller needs a live AR instance for a
framework integration point that requires one (e.g. Devise's `sign_in(user)`
needs a real `User`, not a struct — see `Authentication::SignIn::Command`),
it re-fetches with `User.find(id)` rather than the struct smuggling the AR
object through.

**Pattern**: like every other `app/*` subdirectory, Rails autoloads
`app/structs` as its own root, so a domain's existing top-level module name
is reused rather than nested under a `Structs` namespace:

```ruby
# app/structs/authentication/registered.rb
module Authentication
  class Registered < Dry::Struct
    attribute :user_id, Types::Strict::String
    attribute :user_email, Types::Strict::String
    attribute :organization_id, Types::Strict::String
    attribute :organization_name, Types::Strict::String
  end
end
```

```ruby
# domains/authentication/domain/register_user/command.rb
Success(Authentication::Registered.new(
  user_id: user.id,
  user_email: user.email,
  organization_id: organization.id,
  organization_name: organization.name
))
```

---

### `/app/models`

**Purpose**: Persistence and associations only.

**Contains**:
- Thin models with associations
- Basic validations
- Enums and scopes
- No business logic

**Pattern**:
```ruby
class Artifact < ApplicationRecord
  belongs_to :project
  belongs_to :owner, class_name: 'User'
  has_many :outgoing_relationships, class_name: 'ArtifactRelationship'

  validates :title, presence: true
  enum status: { draft: 0, active: 1, archived: 2 }
end
```

### DI Container: dry-rails

The DI container is **not** hand-rolled — it's the `dry-rails` gem (Rails integration for `dry-system`), not just the lower-level `dry-container`/`dry-auto_inject` gems directly. Adding `gem "dry-rails"` and naming the Rails app module `AverisOS` (in `config/application.rb`) is enough for its railtie to auto-create two constants at boot: `AverisOS::Container` (a `Dry::System::Container` subclass) and `AverisOS::Deps` (the injector for `include Deps[...]`).

**What you write** — `config/initializers/system.rb`, which is `class_eval`'d against the container:
```ruby
Dry::Rails.container do
  register("services.event_dispatcher") { Shared::EventDispatcher.new }

  # As repositories/domain services are built:
  # register("repositories.artifact") { Shared::BaseRepository.new(model_class: Artifact) }
  # register("domains.traceability") { Traceability::TraceabilityService.new(container: AverisOS::Container) }
end
```

**Resolving a dependency directly**:
```ruby
AverisOS::Container["services.event_dispatcher"]
```

**Auto-injection via `Deps`** — preferred inside domain operations, since it avoids hand-writing `initialize(foo:, bar:)` boilerplate for every class:
```ruby
module Traceability
  module LinkArtifacts
    class Command
      include AverisOS::Deps["services.event_dispatcher"]

      def call(request, source:, target:)
        # @event_dispatcher is injected automatically (name is the key's
        # last segment); still overridable with a keyword arg in tests.
        ...
        @event_dispatcher.dispatch(ArtifactsLinked.new(...))
      end
    end
  end
end
```

`/lib` remains for infrastructure code that isn't the container itself — middleware, non-Rails CLI helpers, etc.

## Dependency Flow

The dependency flow in AverisOS is **one-way**:

```
Controllers
    ↓
Domain Services
    ↓
Operations (Request/Verify/Validate/Command)
    ↓
Repositories
    ↓
Models (Persistence)
```

**Rules**:
- ✓ Controllers call domain services
- ✓ Domain services call operations
- ✓ Operations call repositories
- ✓ Operations emit events
- ✓ Other domains subscribe to events
- ❌ Models should NOT call services or operations
- ❌ Operations should NOT call other operations directly (use service composition)
- ❌ Domain A should NOT import from domain B (use events instead)

## Adding a New Domain

When adding a new domain:

1. **Create the domain directory**:
   ```bash
   mkdir -p domains/new_domain/domain/events
   mkdir -p domains/new_domain/spec
   ```

2. **Create the service entry point**:
   ```ruby
   # domains/new_domain/domain/new_domain_service.rb
   module NewDomain
     class NewDomainService
       def initialize(container:)
         @container = container
       end

       def operation_name(params)
         # Orchestrate Request/Verify/Validate/Command
       end
     end
   end
   ```

3. **Create operations**:
   ```bash
   mkdir -p domains/new_domain/domain/operation_name
   touch domains/new_domain/domain/operation_name/{request,verify,validate,command}.rb
   ```

4. **Register in container**:
   ```ruby
   # config/initializers/container.rb
   Container.register('domains.new_domain') do
     NewDomain::NewDomainService.new(container: Container)
   end
   ```

5. **Subscribe to events** (if needed):
   ```ruby
   # config/initializers/event_subscriptions.rb
   event_dispatcher.subscribe(SomeEvent) do |event|
     NewDomain::NewDomainService.new(container: Container).handle_event(event)
   end
   ```

## Cross-Domain Communication

Domains **should not** import from each other. Instead, they communicate via **events**.

### ❌ Wrong: Direct import
```ruby
# In GitIntegration domain
class DetectRelatedArtifacts
  def call(commit)
    artifact = Traceability::FindArtifact.call(commit.message)  # ❌ Direct import!
  end
end
```

### ✓ Right: Event-driven
```ruby
# In GitIntegration domain
class SyncCommits
  include Dry::Monads[:result]

  def call(commit)
    # Emit event for other domains
    @event_dispatcher.dispatch(
      CommitSynced.new(hash: commit.hash, message: commit.message)
    )
    Success()
  end
end

# In Traceability domain (subscribed to CommitSynced)
class CommitSyncedHandler
  def call(event)
    related = FindRelatedArtifacts.new(repositories: @repositories)
    result = related.call(event.message)
    if result.success?
      # Link the commit to artifacts
    end
  end
end
```

## Testing Domains

Each domain should have comprehensive tests:

```
domains/traceability/spec/
├── create_artifact_spec.rb
├── link_artifacts_spec.rb
├── impact_analysis_spec.rb
└── find_related_spec.rb
```

Test each phase independently:

```ruby
describe Traceability::CreateArtifact::Verify do
  # Unit tests - no DB, no mocks
  it "validates input format"
end

describe Traceability::CreateArtifact::Validate do
  # Integration tests - with DB
  it "checks project exists"
end

describe "CreateArtifact Integration" do
  # E2E tests
  it "creates artifact and emits event"
end
```

## Future Extraction to Microservices

When a domain is ready to be extracted in Phase 3+:

1. **Create separate repo** for the domain
2. **Extract shared code** to shared gems (dry-rb patterns, Result monad, etc.)
3. **Replace direct calls** with HTTP API calls
4. **Keep event communication** the same (messages/queues)

The domain boundary is already clear in the monorepo structure, so extraction is straightforward.

---

## Summary

The monorepo structure:
- **Keeps domains isolated** with clear boundaries
- **Enables fast development** by keeping everything together
- **Makes extraction easy** when needed
- **Enforces good practices** through dependency direction
- **Supports testing** at multiple levels

When in doubt: **Keep domains isolated, communicate via events, extract when ready.**
