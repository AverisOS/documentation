# Architecture Overview

AverisOS is built on domain-driven design (DDD) principles with three bounded contexts communicating via events. The system separates **Rails API** (JSON-only, stateless) from frontend (Vite + React SPA), deployed independently with zero-downtime strategies.

## Rails API Mode

AverisOS backend runs exclusively in **Rails API mode**:

- **No HTML views or templates** — only JSON responses via serializers
- **No asset pipeline** — CSS/JS managed by React frontend
- **Stateless operations** — each request is independent; no server-side sessions
- **Token-based authentication** — Bearer tokens in Authorization header
- **CORS-enabled** — frontend on different domain communicates via HTTPS/REST
- **Lightweight middleware** — only what's needed for JSON APIs

Initialize with `rails new --api`:
```bash
rails new averis-os --api --database=postgresql
```

All API responses are JSON (never HTML):

```ruby
# Controller example
class Api::V1::UsersController < Api::BaseController
  def create
    render json: UserSerializer.new(user)  # JSON only
  end
end
```

## Bounded Contexts

### Authentication Domain
Handles user registration, login, session management, and password reset. Produces events like `UserRegistered`, `SessionStarted`, `PasswordReset`.

### Traceability Domain
Core domain managing artifacts (specs, code, tests, docs) and relationships between them. Provides impact analysis and dependency graph queries. Produces events like `ArtifactCreated`, `RelationshipEstablished`.

### Git Integration Domain
Connects to Git repositories, syncs commits, and links them to artifacts. Produces events like `RepositoryConnected`, `CommitsSync'd`.

## Design Patterns

### Domain-Driven Design (DDD)
- **Bounded Contexts**: Each domain has clear boundaries and responsibilities
- **Aggregates**: Aggregate roots (User, Artifact, Repository) manage consistency
- **Events**: Loose coupling via domain events, not direct imports
- **Repositories**: Abstract persistence per domain
- **Value Objects**: Immutable, reusable objects (UserId, ArtifactId)

### RVVC Pattern (Selective)
Applied when operation complexity warrants (2+ criteria):
1. **Request**: Parse/validate input
2. **Verify**: Check preconditions (user exists, no duplicates)
3. **Validate**: Apply business rules
4. **Command**: Perform persistence

Example: `RegisterUser` uses all 4 layers. Simple `GetArtifact` uses only Command.

### Result Monad
All operations return `Result<T, Error>` (success or typed failure):
```ruby
result = register_user(params)
result.on_success { |user| render json: user }
result.on_failure { |error| render json: error, status: :unprocessable_entity }
```

### Dependency Injection
Container manages all dependencies. Services receive what they need—no hidden globals or singletons.

### Event-Driven Communication
Domains communicate via events published to an event bus, consumed asynchronously by Sidekiq. This enables loose coupling and async processing.

## Deployment Strategy

### Zero-Downtime Deployments
- **Frontend**: CDN serves new version instantly with asset versioning
- **Backend (Rails API)**: Blue-green deployment strategy—new version runs alongside old, traffic switches gradually
- **Database**: Backward-compatible migrations deployed before code changes

### Environments
- **Development**: Local Rails API + React dev server
- **Staging**: Full production setup for validation
- **Production**: Live user environment with backups and monitoring

## Key Principles

1. **Clear Separation of Concerns**: Each domain owns its data and logic
2. **API-First Design**: Rails API responses are JSON, never HTML
3. **Testability**: Units testable in isolation; integration tests validate flows
4. **Observability**: Structured logging, distributed tracing, error tracking
5. **Scalability**: Stateless backend; microservice extraction path built in
6. **Developer Experience**: Local development mirrors production; fast feedback loops
