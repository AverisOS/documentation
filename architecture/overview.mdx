# Architecture Overview

AverisOS is built on domain-driven design (DDD) principles with three bounded contexts communicating via events. The system separates **Rails API** (JSON-only, stateless) from frontend (Vite + React SPA), deployed independently with zero-downtime strategies.

## Rails API Mode

AverisOS backend runs exclusively in **Rails API mode**:

- **No HTML views or templates** — only JSON responses via serializers
- **No asset pipeline** — CSS/JS managed by React frontend
- **Stateless operations** — each request is independent; no server-side sessions
- **Token-based authentication** — Bearer tokens in Authorization header
- **CORS-enabled** — frontend on different domain communicates via HTTPS/REST
- **Lightweight middleware** — only what's needed for JSON APIs

Initialize with `rails new --api`:
```bash
rails new averis-os --api --database=postgresql
```

All API responses are JSON (never HTML):

```ruby
# Controller example
class Api::V1::UsersController < Api::BaseController
  def create
    render json: UserSerializer.new(user)  # JSON only
  end
end
```

## Bounded Contexts

### Authentication Domain
Handles user registration, login, session management, and password reset. Produces events like `UserRegistered`, `SessionStarted`, `PasswordReset`.

### Traceability Domain
Core domain managing artifacts (specs, code, tests, docs) and relationships between them. Provides impact analysis and dependency graph queries via a Postgres closure table (see [ADR-011](../decisions/adr-011-graph-modeling.mdx)). Produces events like `ArtifactCreated`, `RelationshipEstablished`.

### Git Integration Domain
Connects to Git repositories, syncs commits, and links them to artifacts. Produces events like `RepositoryConnected`, `CommitsSync'd`.

## Design Patterns

### Domain-Driven Design (DDD)
- **Bounded Contexts**: Each domain has clear boundaries and responsibilities
- **Aggregates**: Aggregate roots (User, Artifact, Repository) manage consistency
- **Events**: Loose coupling via domain events, not direct imports
- **Repositories**: Abstract persistence per domain
- **Value Objects**: Immutable, reusable objects (UserId, ArtifactId)

### RVVC Pattern (Selective)
The four-phase pattern (Request → Verify → Validate → Command) is **not required for every operation**. Use the full pattern only when an operation meets 2 or more of:
- Crosses domain boundaries or emits events other domains subscribe to
- Has semantic validation beyond existence checks (circular dependency detection, permission checks, uniqueness across related records)
- Belongs to a critical path (artifact creation/linking, auth, anything security- or billing-relevant)
- Has business rules that would otherwise hide inside a controller or model

Otherwise, collapse to a lightweight **Validate → Command** (or just **Command**) pair — trivial reads and simple CRUD don't need four files each.

Example: `LinkArtifacts` (circular dependency check, cross-domain event) uses all 4 layers. `GetArtifact` (a read) uses only Command. `UpdateArtifactTitle` (simple field update, no side effects) uses Validate → Command.

See [ADR-001](../decisions/adr-001-ddd.mdx) and [Design Principles §6](./design-principles.mdx#6-four-phase-operations-selective) for the full rationale, and [Patterns](./patterns.mdx#pattern-0-lightweight-operation-no-side-effects) for a worked lightweight example.

### Result Monad
All operations return `Result<T, Error>` (success or typed failure):
```ruby
result = register_user(params)
result.on_success { |user| render json: user }
result.on_failure { |error| render json: error, status: :unprocessable_entity }
```

### Dependency Injection
`dry-rails` (not raw `dry-container`) provides `AverisOS::Container` and the `AverisOS::Deps` auto-injection mixin. Services receive what they need — no hidden globals or singletons. See [Monorepo Structure](./monorepo-structure.mdx#di-container-dry-rails).

### Event-Driven Communication
Domains communicate via events published to an in-process `EventDispatcher`, handled **synchronously in the same request** for Phase 1 — no queue, no Sidekiq. This keeps failures visible immediately (a failing subscriber shows up in the same request instead of silently disappearing into a queue) and avoids operating a job system before it's needed. See [ADR-006](../decisions/adr-006-event-dispatcher.mdx) for the revisit trigger for moving to async.

## Deployment Strategy

### Zero-Downtime Deployments
- **Frontend**: CDN serves new version instantly with asset versioning
- **Backend (Rails API)**: Blue-green deployment strategy—new version runs alongside old, traffic switches gradually
- **Database**: Backward-compatible migrations deployed before code changes

### Environments
- **Development**: Local Rails API + React dev server
- **Staging**: Full production setup for validation
- **Production**: Live user environment with backups and monitoring

| Layer | Technology | Purpose |
|-------|-----------|---------|
| Frontend | React 18 + Vite | Fast SPA build/dev |
| UI Framework | shadcn/ui + Tailwind | Customizable components |
| Graph Visualization | react-flow (`@xyflow/react`) + elkjs | Impact analysis / dependency graph rendering (see [ADR-012](../decisions/adr-012-impact-visualization.mdx)) |

| Language | Ruby 3.4.x | Productive, readable |

| Database | PostgreSQL 15+ | Reliable RDBMS; also stores the artifact graph (see [ADR-011](../decisions/adr-011-graph-modeling.mdx)) |
| Event Dispatch | In-process `EventDispatcher` | Synchronous cross-domain events (Phase 1) |
| Cache / Job Queue | Redis + Sidekiq | **Phase 2+** — not needed while events are synchronous |
| Testing | Playwright, RSpec, Capybara | E2E, unit, integration |
| Deployment | GitHub Actions, Heroku/Railway | CI/CD automation |
| Monitoring | Sentry, OpenTelemetry, Prometheus | Errors, traces, metrics |

## Key Principles

1. **Clear Separation of Concerns**: Each domain owns its data and logic
2. **API-First Design**: Rails API responses are JSON, never HTML
3. **Testability**: Units testable in isolation; integration tests validate flows
4. **Observability**: Structured logging, distributed tracing, error tracking
5. **Scalability**: Stateless backend; microservice extraction path built in
6. **Developer Experience**: Local development mirrors production; fast feedback loops
