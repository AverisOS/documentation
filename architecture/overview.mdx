# Architecture Overview

## Quick Summary

- **Language:** Ruby 3.2+
- **Framework:** Rails 7+
- **Pattern:** Domain-Driven Design (DDD)
- **Key Libraries:** dry-rb, PostgreSQL, Redis
- **Error Handling:** Result monad (no exceptions for expected errors)
- **Structure:** Monorepo with domain-bounded contexts

## Design Philosophy

### Core Principles

1. **Business Logic is First-Class** — Lives in domain services, not models
2. **Models are Thin** — Persistence and associations only
3. **Controllers Route Only** — Extract params, call service, serialize
4. **All Dependencies Injected** — No hidden dependencies, no global state
5. **Result Monad for Errors** — Explicit error handling, composable operations
6. **Four-Phase Operations** — Request → Verify → Validate → Command

### Why This Approach?

- **Scalability:** Domains can be extracted to microservices
- **Testability:** Each phase is tested independently
- **Maintainability:** Business logic is explicit and central
- **Flexibility:** Easy to swap implementations
- **Team Cognition:** Clear structure for new engineers

## Architecture Layers

```
┌─────────────────────────────────────┐
│    HTTP Layer (Controllers)         │ ← Routing, serialization
├─────────────────────────────────────┤
│  Application Layer (Domain Services)│ ← Orchestration
├─────────────────────────────────────┤
│    Domain Layer (Operations)        │ ← Business logic ★
├─────────────────────────────────────┤
│   Infrastructure Layer (Models)     │ ← Persistence
└─────────────────────────────────────┘
```

Each layer has a specific responsibility:

- **HTTP Layer:** Convert HTTP requests to domain calls, serialize responses
- **Application Layer:** Orchestrate operations, coordinate between domains
- **Domain Layer:** Business logic, decision making, validation
- **Infrastructure Layer:** Data persistence, database access

## Key Patterns

### 1. Result Monad

All operations return `Result<T, E>` instead of raising exceptions.

```ruby
result = service.create_artifact(...)

result
  .and_then { |artifact| link_artifacts(artifact) }
  .map { |artifact| serialize(artifact) }
  .match do |r|
    if r.success?
      render json: { data: r.value }
    else
      render json: { error: r.error }, status: 422
    end
  end
```

Benefits:
- Error paths are explicit in code
- Operations are composable with `and_then`, `map`
- No exception overhead for expected errors
- Easy to test both success and failure

### 2. Four-Phase Operations

Every domain operation follows: **Request → Verify → Validate → Command**

```ruby
module SomeDomain
  module OperationName
    class Request
      # Input parameters, immutable
    end

    class Verify
      # Check syntax/format, NO database access
      # Return failure fast if malformed
    end

    class Validate
      # Check semantics with database
      # Existence checks, permissions, business rules
      # Prefetch data to avoid N+1 in Command
    end

    class Command
      # Execute the operation
      # Should have high confidence of success
      # Emit domain events
    end
  end
end
```

### 3. Domain Services

Entry point for each domain. Orchestrates operations.

```ruby
class TraceabilityService
  def initialize(artifact_repo:, relationship_repo:, event_dispatcher:)
    @artifact_repo = artifact_repo
    @relationship_repo = relationship_repo
    @event_dispatcher = event_dispatcher
  end

  def create_artifact(project_id:, type:, title:, owner_id:)
    request = CreateArtifact::Request.new(...)
    
    CreateArtifact::Verify.call(request)
      .and_then { |req| CreateArtifact::Validate.call(req, @artifact_repo) }
      .and_then { |req| CreateArtifact::Command.call(req, @artifact_repo, @event_dispatcher) }
  end
end
```

### 4. Dependency Injection

All dependencies registered in a container:

```ruby
AverisOS::Container.register('domains.traceability') do
  Traceability::Service.new(
    artifact_repo: Container['repositories.artifact'],
    event_dispatcher: Container['services.event_dispatcher']
  )
end
```

### 5. Events for Cross-Domain Communication

Domains emit events that other domains subscribe to:

```ruby
# Domain A: Emit event
@event_dispatcher.dispatch(ArtifactCreated.new(artifact_id: artifact.id))

# Domain B: Subscribe
event_dispatcher.subscribe(ArtifactCreated) { |event| handle(event) }
```

This keeps domains loosely coupled and easy to extract.

## Controllers (Thin)

Controllers only handle HTTP concerns:

```ruby
class ArtifactsController < ApplicationController
  def create
    service = AverisOS::Container['domains.traceability']
    result = service.create_artifact(
      project_id: params[:project_id],
      type: params[:type],
      title: params[:title],
      owner_id: current_user.id
    )

    if result.success?
      render json: { data: ArtifactSerializer.new(result.value) }, status: 201
    else
      render json: { error: result.error }, status: 422
    end
  end
end
```

## Models (Thin)

Models for persistence only:

```ruby
class Artifact < ApplicationRecord
  belongs_to :project
  belongs_to :owner, class_name: 'User'
  has_many :relationships

  validates :title, presence: true, length: { maximum: 500 }
  validates :type, inclusion: { in: VALID_TYPES }

  enum status: { draft: 0, active: 1, archived: 2 }
end
```

No business logic in models. Ever.
