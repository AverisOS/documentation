# ADR-002: Result Monad Instead of Exceptions

**Date**: September 2026  
**Status**: ✅ Accepted  
**Author**: Aaron

---

## Context

Ruby and Rails traditionally use exceptions for error handling. For unexpected errors (database corruption, network failures), exceptions make sense. But for **expected errors** (invalid input, resource not found, permission denied), exceptions create problems:

- **Silent failures**: If a developer forgets to catch an exception, the error disappears
- **Invisible error paths**: Method signatures don't show what errors can occur
- **Performance overhead**: Exception handling is expensive in Ruby
- **Mixing error handling with control flow**: Makes code harder to reason about

Example of traditional Rails approach:
```ruby
def create_artifact(params)
  raise "Invalid project" if Project.find(params[:project_id]).nil?  # ❌
  raise "Missing title" if params[:title].blank?                     # ❌
  artifact = Artifact.create!(params)
  artifact
rescue StandardError => e
  handle_error(e)
end
```

Problems with this approach:
- Exception raised in line 2 vs. line 4 is unclear to the caller
- If caller forgets `rescue`, the error propagates unexpectedly
- Performance hit from raising exceptions
- Hard to test both success and failure paths

---

## Decision

Use a **Result monad** (success/failure) for expected errors, built on **dry-monads**'
`Success`/`Failure` types rather than a hand-rolled class (see
[Implementation Note](#implementation-note-dry-monads-instead-of-a-custom-class) below):

```ruby
class ArtifactService
  include Dry::Monads[:result]

  def create_artifact(params)
    project = repository.find_project(params[:project_id])
    return Failure("Project not found") unless project

    return Failure("Title is required") if params[:title].blank?

    artifact = repository.create_artifact(params)
    @event_dispatcher.dispatch(ArtifactCreated.new(artifact_id: artifact.id))

    Success(artifact)
  end
end

# Caller always knows what to expect
result = service.create_artifact(params)
if result.success?
  render json: result.value!
else
  render json: { error: result.failure }, status: 422
end
```

---

## Alternatives Considered

### 1. Exceptions (Status Quo)
**Pros**: Rails convention, familiar to most developers  
**Cons**: Silent failures, invisible error paths, performance overhead for expected errors

**Verdict**: Good for bugs, bad for expected errors.

### 2. Tuples `[success, value, error]`
**Pros**: Simple, explicit  
**Cons**: Less ergonomic, can't chain operations easily, easy to forget to check result

**Verdict**: Works but less composable.

### 3. Try Types (like Swift/Kotlin)
**Pros**: Type-safe, explicit  
**Cons**: Not mature in Ruby ecosystem

**Verdict**: Good idea, poor Ruby support.

---

## Rationale

### ✓ Visibility
Error paths are **explicit in code**:
```ruby
# Clear what can fail
result = create_artifact(params)
       .bind { |artifact| link_to_requirement(artifact) }
       .bind { |artifact| notify_watchers(artifact) }

# Obvious that we handle failures
result.success? ? render_success(result.value!) : render_error(result.failure)
```

### ✓ Composability
Chain operations elegantly:
```ruby
Service.create(params)
  .bind { |item| validate(item) }
  .fmap { |item| transform(item) }
  .bind { |item| save(item) }
  .either(->(item) { handle_success(item) }, ->(error) { handle_error(error) })
```

### ✓ Performance
No exception overhead for expected errors:
- Exceptions in Ruby are **very expensive** (stack unwinding, allocation)
- Result monad is just a simple object
- Better performance for high-volume operations

### ✓ Testing
Easy to test both paths:
```ruby
# Success case
result = service.create_artifact(valid_params)
expect(result).to be_success
expect(result.value!).to be_a(Artifact)

# Failure case
result = service.create_artifact(invalid_params)
expect(result).to be_failure
expect(result.failure).to include("Title is required")
```

### ✓ Clarity
Developers immediately see all possible outcomes:
```ruby
# Not: "This method might raise an exception"
# But: "This method returns a Result with success? method"
result = create_artifact(...)
if result.success?
  # We have a valid artifact, via result.value!
else
  # We have a clear error message, via result.failure
end
```

---

## Consequences

### ✅ Positive
- Error paths are **explicit** in code
- Operations are **composable** and chainable
- **No performance penalty** for expected errors
- **Clear semantics**: success or failure, never ambiguous
- **Easier testing**: test both paths without exception handling

### ⚠️ Negative
- **Different from Rails conventions**: Rails developers expect exceptions
- **More verbose**: Every method returns Result instead of raising
- **Chaining syntax**: Some developers find `bind`/`fmap` unfamiliar
- **No unified accessor**: unlike a hand-rolled Result, dry-monads' `Success`/`Failure`
  don't share a `.value`/`.error` interface — callers must check `success?` first, then
  call `.value!` (raises on Failure) or `.failure` (only defined on Failure)
- **Legacy integration**: If calling Rails code, must handle its exceptions

### 🛡️ Mitigation
- Provide [examples and patterns](../architecture/patterns.mdx)
- Document the rationale in architecture guide
- Offer wrapper methods for Rails code that raises exceptions
- Team training on Result monad usage

## Implementation Note: dry-monads instead of a custom class

The Result type was originally a hand-rolled `Shared::Result` class living in
`domains/shared/lib/result.rb`. It has since been replaced with
[dry-monads](https://dry-rb.org/gems/dry-monads/)'s `Result` module (`Success`/`Failure`),
for a few reasons:

- **Less code to maintain**: the custom class duplicated what a well-tested library
  already provides, for no behavioral gain.
- **Already in the dependency tree**: this codebase already pulls in `dry-struct` and
  `dry-validation` (see [ADR-005](./adr-005-dry-rb.mdx)) — `dry-monads` is the same
  family and shares its conventions.
- **Richer combinator set**: `bind` (chain, equivalent to the old `and_then`), `fmap`
  (map over the success value), `or`/`or_fmap`, `either`, and pattern-matching via
  `case ... in Success(value) / in Failure(error)` — more than the hand-rolled class
  offered.

**One real tradeoff**: the custom `Shared::Result` supported an extra `data:` kwarg
payload alongside `value`/`error` (`Shared::Result.success(value, **data)`). Nothing in
the shipped codebase ever used it, but [patterns.mdx](../architecture/patterns.mdx)
documented a planned use for it — passing prefetched records (e.g. `source`/`target`
artifacts) from a `Validate` phase forward into a `Command` phase without a second
lookup. `dry-monads`' `Success`/`Failure` take exactly one payload, so that pattern is
now expressed by bundling the extra values into a plain `Struct` and returning *that*
struct as the single `Success` value — the same approach
`Authentication::RegisterUser::Command` already uses for its two-value `user` +
`organization` result:

```ruby
module Authentication
  module RegisterUser
    Registered = Struct.new(:user, :organization, keyword_init: true)

    class Command
      include Dry::Monads[:result]
      # ...
      def call(request)
        # ...
        Success(Registered.new(user: user, organization: organization))
      end
    end
  end
end
```

See `patterns.mdx`'s "Example: Link Artifacts with Circular Dependency Detection" for
the equivalent applied to a multi-record prefetch.

## Implementation

### Real Usage: Authentication::RegisterUser

```ruby
# Verify — schema-shape checks (dry-validation contract), class method
module Authentication
  module RegisterUser
    class Verify < Dry::Validation::Contract
      extend Dry::Monads[:result]

      params do
        optional(:email).maybe(:string)
        optional(:password).maybe(:string)
        optional(:organization_name).maybe(:string)
      end

      # ... rules ...

      def self.call(request)
        result = new.call(
          email: request.email,
          password: request.password,
          organization_name: request.organization_name
        )

        return Success(request) if result.success?
        Failure(result.errors.to_a.first.text)
      end
    end
  end
end
```

```ruby
# Validate — business-rule checks needing a DB lookup, instance method
module Authentication
  module RegisterUser
    class Validate < Dry::Validation::Contract
      include Dry::Monads[:result]

      option :user_repository
      option :organization_repository

      # ... rules ...

      def call(request)
        result = super(
          normalized_email: request.normalized_email,
          organization_slug: request.organization_slug
        )

        return Success(request) if result.success?
        Failure(result.errors.to_a.first.text)
      end
    end
  end
end
```

```ruby
# Command — executes the write, bundles multiple return values into a Struct
module Authentication
  module RegisterUser
    Registered = Struct.new(:user, :organization, keyword_init: true)

    class Command
      include Dry::Monads[:result]
      include AverisOS::Deps[
        user_repository: "repositories.user",
        organization_repository: "repositories.organization",
        organization_membership_repository: "repositories.organization_membership",
        event_dispatcher: "services.event_dispatcher"
      ]

      def call(request)
        # ... create user, organization, membership in a transaction ...

        @event_dispatcher.dispatch(UserRegistered.new(user_id: user.id, organization_id: organization.id))
        Success(Registered.new(user: user, organization: organization))
      rescue ActiveRecord::RecordInvalid => e
        Failure(e.record.errors.full_messages.join(", "))
      end
    end
  end
end
```

```ruby
# Composing the three phases
module Authentication
  class AuthenticationService
    def register_user(email:, password:, organization_name:)
      request = RegisterUser::Request.new(email: email, password: password, organization_name: organization_name)

      RegisterUser::Verify.call(request)
        .bind { RegisterUser::Validate.new.call(request) }
        .bind { RegisterUser::Command.new.call(request) }
    end
  end
end
```

### Usage Pattern in a Controller

```ruby
class Api::V1::RegistrationsController < Devise::RegistrationsController
  def create
    result = Authentication::AuthenticationService.new.register_user(
      email: params[:email],
      password: params[:password],
      organization_name: params[:organization_name]
    )

    if result.success?
      registered = result.value!
      sign_in(registered.user)
      render json: {
        user: { id: registered.user.id, email: registered.user.email },
        organization: { id: registered.organization.id, name: registered.organization.name }
      }, status: :created
    else
      render json: { error: result.failure }, status: :unprocessable_entity
    end
  end
end
```

## When to Use Exceptions

**Still use exceptions for**:
- Bugs in the application (programming errors)
- Unexpected system failures (database down, disk full)
- Configuration errors (missing ENV variables)

**Don't use exceptions for**:
- Validation errors (invalid input)
- Business logic failures (resource not found)
- Permission errors (user not authorized)
- Expected error conditions
