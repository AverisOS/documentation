# Work Management Model

**Phase scope**: The ownership/assignment model below (Projects → Teams → Individuals, backlogs, triage) is **Phase 1** — it's what makes artifacts accountable, which traceability depends on. Formal **Sprint** entities/ceremony and multi-methodology support (Kanban, Waterfall) are **Phase 2** — see [PRD: "Why the Phase Boundary Is Drawn Here"](./prd.mdx#why-the-phase-boundary-is-drawn-here). In Phase 1, `artifacts.status` stops at `in_progress`/`completed` directly from `team_backlog` — there is no `sprint` state or `sprints` table until Phase 2.

## Overview

Work flows from Project ownership through Team assignment to Individual execution. This model supports n:m team-to-domain relationships while maintaining clear accountability.

---

## Core Entities

### Projects
- **Owned by**: Individual user (project owner)
- **Status**: draft, ready_for_work
- **Access**: Access groups holding `contribute`/`review`/`manage`/`admin` on
  the project via `permission_grants` — see
  [Domains Overview → Authorization](../domains/overview.mdx#2a-authorization).
  There is no dedicated `project_teams` table; "which teams can contribute"
  is answered by which access groups a team's members belong to.
- **Backlog**: Visible to project owner + anyone with `view`-or-above access

### Teams
- **Membership**: Explicit (`team_memberships`, a plain join — no role column)
- **Access**: Team's own relation vocabulary (`viewer`/`editor`/`admin`),
  granted to access groups via `permission_grants` — the same mechanism as
  Project access, not a separate "domain access" concept
- **Backlogs**:
  - Project backlog: Items from assigned projects
  - Team backlog: Items claimed by the team
  - Sprint backlog: Items committed for a sprint (**Phase 2**)

### Artifacts (Work Items)
- **Assignment chain**: Project → Team → Individual
- **States (Phase 1)**: unassigned → team_backlog → in_progress → completed (Phase 2 inserts a `sprint` state between `team_backlog` and `in_progress`)
- **Ownership**: Team that will deliver it (final responsibility)

## Work Assignment Flow

### 1. Project Initialization

```
Individual (Project Owner)
  ├─ Creates project
  ├─ Marks as "ready_for_work"
  └─ Grants an access group contribute/review access on the project
     (permission_grants — see the authorization domain)
```

### 2. Item to Team Backlog

**Two paths:**

#### A. Team Self-Assignment (Pull Model)
- Team sees project backlog item
- Team drags/assigns to own backlog
- Status: team_claimed

#### B. Project Owner Flags (Push Model)
- Project owner flags item for team
- Creates flagged_item record
- Team receives notification
- Team can:
  - Accept → moves to backlog (status: team_accepted)
  - Reassign → sends to different team
  - Conflict → escalates to triage pool

### 3. Assignment Resolution

**Normal Case:**
```
flagged_item → team_accepted → team_backlog
```

**Conflict Case:**
```
multiple teams flagged
  → triage_pool (leadership reviews)
  → assigned_by_management (marked for tracking)
  → team_backlog
```

**Tracking:**
- `assignment_source`: "team_self" | "owner_flagged" | "management_assigned"
- Metric: ratio of management_assigned vs team_accepted (org health signal)

### 4. Sprint Assignment — Phase 2

**Requirement:** All sprint items must have team ownership
```
artifact_state = team_backlog
  → team commits to sprint
  → sprint_item created with (team_id, artifact_id)
  → ready for individual assignment
```

> **Phase 1 note**: There is no formal sprint ceremony yet. An artifact moves `team_backlog → in_progress` directly once a team starts work on it; the `sprints`/`sprint_items` tables and this step arrive in Phase 2 alongside Kanban/Waterfall support.

### 5. Individual Assignment

**Separate from team ownership:**
```
artifact → team (who delivers)
artifact → individual (who does the work)
```

Individual assignment can be:
- Direct: user assigned to artifact
- Inferred: git commits, PR authorship
- Updated: during execution

## Ownership & Accountability

### Team Ownership
- **Responsible for**: Completing artifact, meeting acceptance criteria, quality
- **Visible in**: Team backlog, sprint, traceability
- **Metric**: Team velocity, completion rate, defect escape

### Individual Ownership
- **Responsible for**: Day-to-day progress, technical decisions, code quality
- **Visible in**: Work logs, git history, PR reviews
- **Metric**: Productivity, code review participation

### Project Owner Responsibility
- **Responsible for**: Project backlog, prioritization, team coordination
- **Visible in**: Project health, scope management
- **Metric**: Project on-time delivery, scope changes

## Permissions & Access

Actual enforcement lives entirely in the authorization domain
(`AuthorizationService#can?`), not in work-management-specific columns or
tables. This section describes which of that domain's relations govern each
work-management action; see
[`2026-09-07-authorization-system-design.md`](https://github.com/AverisOS/backend/blob/main/docs/superpowers/specs/2026-09-07-authorization-system-design.md)
for the full permission vocabulary and
[`2026-09-09-access-groups-design.md`](https://github.com/AverisOS/backend/blob/main/docs/superpowers/specs/2026-09-09-access-groups-design.md)
for how grants are held (always via an `AccessGroup`, including
lazily-created personal groups for individual grants).

### Project-Level
- `admin`/`manage`: full control (settings, team access, deletion)
- `contribute`: create/edit artifacts, claim project backlog items into a
  team backlog
- `review`: comment, approve/reject — independent of `contribute`, so a
  reviewer need not also be a contributor
- `view`: read-only visibility into the project backlog
- No grant on the project at all: no access, unless the org role
  (`owner`/`admin`) cascades it

### Team-Level
- The team's own `viewer`/`editor`/`admin` relation (held by an access
  group, not a per-membership role column) determines who can view the team
  backlog, commit items to a sprint, and reassign flagged items

### Artifact-Level
- Falls back to the parent project's relation by default (a project
  `contribute` grant already covers artifact edits); a direct grant on one
  artifact is only needed for exceptions (e.g. one external reviewer on one
  artifact) — see "Computed permissions" in the authorization design for the
  creator-based delete/archive rules

## Data Model

### Core Tables

```sql
projects(
  id,
  owner_user_id,
  name,
  status,  -- draft | ready_for_work
  created_at,
  updated_at
)

-- Team-to-project access is not a dedicated table -- it's expressed as
-- permission_grants rows (access_group/relation/target), same as every
-- other authorization decision. See the authorization domain's own schema
-- in 2026-09-09-access-groups-design.md rather than duplicating it here.

artifacts(
  id,
  project_id,
  title,
  description,
  status  -- Phase 1: unassigned | team_backlog | in_progress | completed
          -- Phase 2 adds: sprint (between team_backlog and in_progress)
)

artifact_team_assignments(
  artifact_id,
  team_id,
  source,  -- team_self | owner_flagged | management_assigned
  assigned_at,
  accepted_at  -- null if management_assigned
)

artifact_user_assignments(
  artifact_id,
  user_id,
  role,  -- assignee | reviewer | owner
  assigned_at
)

flagged_items(
  artifact_id,
  from_team_id,
  to_team_id,
  status,  -- pending | accepted | reassigned | triaged
  created_at
)

triage_pool(
  artifact_id,
  conflicting_teams,  -- json array
  assigned_by,  -- user_id
  resolved_team_id,
  resolved_at
)

-- Phase 2 (not built in Phase 1):
sprints(
  id,
  team_id,
  name,
  start_date,
  end_date
)

sprint_items(
  sprint_id,
  artifact_id,
  committed_at
)
```

## Queries & Workflows

### Team Backlog

```sql
SELECT a.*
FROM artifacts a
JOIN artifact_team_assignments ata ON a.id = ata.artifact_id
WHERE ata.team_id = ?
AND a.status IN ('team_backlog', 'sprint', 'in_progress')
AND a.project_id IN (
  -- "Projects this team's members have contribute-or-above access to" --
  -- resolved through access groups, not a direct team-to-project table.
  SELECT pg.target_id
  FROM permission_grants pg
  JOIN access_group_memberships agm ON agm.access_group_id = pg.access_group_id
  JOIN team_memberships tm ON tm.user_id = agm.user_id
  WHERE tm.team_id = ?
  AND pg.target_type = 'Project'
  AND pg.relation IN ('contribute', 'manage', 'admin')
)
ORDER BY priority
```

### Assignment Health Metrics

```sql
-- Ratio of team-accepted vs management-assigned
SELECT
  COUNT(CASE WHEN source = 'team_self' THEN 1 END) as team_self,
  COUNT(CASE WHEN source = 'owner_flagged' AND accepted_at IS NOT NULL THEN 1 END) as owner_accepted,
  COUNT(CASE WHEN source = 'management_assigned' THEN 1 END) as management_assigned
FROM artifact_team_assignments
WHERE assigned_at >= DATE_SUB(NOW(), INTERVAL 30 DAY)
```

### Triage Items Needing Resolution

```sql
SELECT tf.artifact_id, tf.conflicting_teams, a.title
FROM triage_pool tf
JOIN artifacts a ON tf.artifact_id = a.id
WHERE tf.resolved_at IS NULL
ORDER BY tf.created_at
```

## Key Design Decisions

1. **Explicit Team Ownership**: All artifacts must be claimed by a team before sprint assignment. This maintains accountability and enables team-level metrics.

2. **Dual Assignment Path**: Both team self-assignment (pull) and project owner assignment (push) are valid. Tracking the source reveals organizational patterns.

3. **Management Override with Visibility**: Project owners can force-assign (needed when teams deadlock), but it's marked and tracked. This enables leadership intervention while measuring when it's needed.

4. **Separate Individual Assignment**: Individual ownership is distinct from team ownership. Supports accurate work tracking, code attribution, and individual contribution metrics.

5. **Triage Pool**: When multiple teams claim an item and can't resolve it, it escalates to a formal review process. Prevents deadlock while maintaining team autonomy.
