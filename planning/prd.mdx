# Product Requirements Document (PRD)

# Product Name

**AverisOS**

From customer intent to production confidence

## 1. Product Vision

Build the AI-native operating system for software delivery.

The platform connects the complete software lifecycle:

Customer Need → Product Strategy → Roadmap → Requirements → Architecture → Implementation → Testing → Release → Customer Outcome

The goal is to eliminate fragmented engineering workflows and create a living engineering knowledge graph that enables humans and AI agents to understand, manage, and improve software delivery.

---

# 2. Problem Statement

Modern software organizations use dozens of disconnected tools:

* Product management tools
* Roadmapping tools
* Issue trackers
* Documentation systems
* Design tools
* Test management platforms
* Source control systems
* CI/CD systems
* Observability platforms
* Customer feedback systems

This creates several problems:

## Lost Context

Teams lose the connection between:

* Why a feature exists
* What customer problem it solves
* What decisions shaped the implementation
* What code changed
* What tests prove correctness
* Whether the release achieved the intended outcome

## Poor Traceability

Organizations cannot easily answer:

* What requirements are impacted by this code change?
* What tests validate this customer commitment?
* What architecture decisions affect this feature?
* What risks exist before release?

## AI Without Context

Current AI tools can generate code, summaries, and documents, but they lack the full product and engineering context required to make meaningful decisions.

# 3. Product Principles

## Engineering Knowledge Graph First

Every artifact is connected.

The platform does not store isolated tickets and documents. It maintains relationships between engineering knowledge.

## AI-Native

AI is a foundational capability, not an assistant added later.

## Model Agnostic

## Cost Conscious

The platform continuously recommends the most efficient AI approach.

## Developer First

Engineers should work primarily through:

* IDE
* Command line
* AI agents

## Evidence Based

Status, readiness, and quality should be derived from evidence.

# 23. MVP

## Phase 1: Core Intelligence Layer + Work Ownership

The foundation layer that connects the entire software delivery lifecycle with explicit team accountability. Scope is deliberately narrowed to the traceability wedge — enough work-ownership context to make artifacts accountable, without building a full Agile delivery tool before the core value proposition is validated. See "Why the Phase Boundary Is Drawn Here" below.

### Intelligence Foundation
* Flexible artifacts
* Unlimited hierarchy
* Traceability graph (Postgres closure table — see [ADR-011](../decisions/adr-011-graph-modeling.mdx))
* Manual testing
* Automated test integration
* MCP foundation
* AI provider abstraction

### Work Ownership & Permissions
* Explicit team membership and roles
* Project ownership and team assignment
* Team and project backlogs (a list of owned/assigned artifacts — not a sprint board)
* Work assignment workflows (pull/push/flagging)
* Triage pool for assignment conflicts
* Separate team and individual accountability
* Role-based + domain-level permissions
* Confidential flag for sensitive projects
* Assignment health metrics (team self vs management assigned) — this is a discovery signal, kept in Phase 1 because it's cheap to compute from the assignment data already being captured, not because it's delivery tooling

### Developer Experience
* CLI (team queries, traceability, assignment commands)

**Not in Phase 1** (see Phase 2/3 below): sprint planning, Kanban/Waterfall workflow support, IDE integration.

---

## Phase 2: Product, Architecture Intelligence & Delivery Workflow

Adds intelligence for customer needs, design, and architectural decisions, and now that traceability itself is validated, the delivery-workflow layer on top of it.

* Customer research
* Roadmaps

* Technical diagrams

* Cost optimization
* **Work Execution**: sprint planning and management, basic Agile workflow support (moved from Phase 1 — see "Why the Phase Boundary Is Drawn Here" below)
* Kanban boards, WIP limits, flow metrics
* Waterfall phases, milestones, stage gates (as needed for hybrid-methodology support)

## Phase 3: Enterprise Platform (Core)

* Compliance workflows
* Advanced governance
* Portfolio intelligence
* Industry-specific solutions
* Approval workflows for high-risk work

---

## Phase 4: Platform Extensibility

Opens the platform up to third parties once the enterprise core is in place.

* Marketplace skills
* Plugin/extensibility system (custom domain creation, webhook publishing)
* Integration marketplace

Split out from Phase 3 because it's a distinct bet — third-party ecosystem investment — that shouldn't gate or be gated by enterprise governance work landing on the same timeline.

---

## Phase 5: IDE Integration

* IDE integration (VS Code, JetBrains) — moved from Phase 1, and pushed past even the enterprise/extensibility work

IDE integration gets its own phase, later than originally planned, because it's real ongoing maintenance surface (two plugin ecosystems) for a channel that isn't proven yet. The CLI (Phase 1) validates the "developers want this in their tool of choice" hypothesis more cheaply, and there's no dependency forcing IDE work earlier — it can wait until everything ahead of it has shipped.

---

## Why the Phase Boundary Is Drawn Here

Sprint planning, Kanban boards, and Waterfall stage-gates are well-solved problems — Jira and Azure DevOps already do this well, and building a competitive version of it doesn't differentiate AverisOS. Building it in Phase 1 would spend MVP time and design-partner attention on the part of the product that's least novel, at the expense of the traceability graph and impact analysis, which are the actual bet.

What Phase 1 keeps from the original work-management scope is the minimum needed for traceability to mean anything: an artifact needs an owning team before "what breaks if I change this?" is a useful question to a real person. That's ownership data, not delivery-workflow tooling — see [PRD's original justification, "Why Work Management is Phase 1"](#why-work-management-is-phase-1) below, which still holds for ownership; it just doesn't require sprints or boards to be true.

---

## Why Work Management is Phase 1

Work management is foundational because:

1. **Traceability requires context** — The knowledge graph is useless without knowing who owns what. Team context is as essential as the artifact itself.

2. **Team backlogs enable usability** — Engineers need a single view of their work across projects. Without team assignments, they're looking at orphaned artifacts.

3. **Permissions depend on it** — Read-everything default with confidential flag requires knowing team membership and domain access.

4. **CLI value is unlocked** — Context like "show me my team's work" requires the work management model to be live. (IDE integration itself is deferred all the way to Phase 5 — see the redrawn phase boundaries above — but the CLI needs the same ownership data now.)

5. **Metrics matter from day one** — Tracking management vs team-assigned work reveals organizational friction early. This is a discovery tool, not just a delivery tool.
